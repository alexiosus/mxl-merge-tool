# Windows-установщик: открытые вопросы

Выжимка из рабочего журнала разработки. Всё перечисленное сверено с кодом на
2026-08-09; пункты, закрытые по ходу работы, сюда не попали.

Ничего из списка не мешает пользоваться установщиком: он собирается, ставится и
удаляется. Это долги, а не дефекты.

## Проверить на живой Windows

Установка, открытие окна настройки, пункт контекстного меню и работа на сетевой
шаре (`\\Mac\...`, с `safe.directory`) уже проверены. Осталось:

- **Обновление поверх установленной версии.** Ни разу не выполнялось на
  настоящей файловой системе. Поднять `APP_VERSION`, собрать, поставить поверх
  текущей и убедиться, что каталог прошлой версии исчез, а контекстное меню и
  запись в «Программах и компонентах» указывают на новую. Логика покрыта
  тестами, но с занятыми файлами Windows ведёт себя иначе, чем временный
  каталог в тестах.
- **Полное удаление.** Ключи Git сняты (`git config --global --get
  merge.mxl.driver` ничего не выводит), ключи реестра удалены, `.gitattributes`
  в репозиториях не тронут, а остатки каталога исчезли после следующего входа в
  систему — их удаляет запись `RunOnce` в `HKCU`.
- **«Программы и компоненты» не показывают кнопки Modify и Repair.** Флаги
  пишутся как `REG_DWORD`; проверка нужна, потому что раньше они были строками
  и кнопки появлялись бы неработающими.
- **`git diff` по изменённому `.mxl` выдаёт текст, а не тишину.** В конфигурацию
  пишется `pythonw.exe`; textconv отдаёт результат в дескриптор 1, но
  подтверждения на реальном Git ещё нет.
- **Реакция антивируса** на распакованный архив и отдельно на лаунчер. Подписи
  у сборки нет.

## Долги в коде

- `WindowsRegistryWriter.delete_tree` не различает «у ключа остались дочерние»
  и «нет прав». Рекурсия и возврат признака успеха уже есть, но отказ по правам
  всё ещё выглядит как обычная неудача.
- При `owns=true` удаление снимает `core.attributesFile`, даже если
  пользователь после установки переставил его на свой файл. Стоит снимать
  только когда файл действительно удалён.
- `strip_attributes_line` приводит файл со смешанными переводами строк к одному
  виду и добавляет перевод строки в конец, если его не было.
- Диалог «MXL Merge Tool удалён» показывается и тогда, когда часть ключей снять
  не удалось; пользователь видит «удалён», а затем сообщение об ошибке.
- В `WindowsEnvironment.find_git` остался локальный псевдоним
  `import shutil as shutil_module` — модульный `shutil` уже импортирован, и
  скрывать нечего.
- Docstring `copy_payload` («replacing what is there») читается так, будто
  каталог очищается целиком; на самом деле заменяются только записи из
  `PAYLOAD_ENTRIES`.
- Текст `report_path_too_long` в лаунчере советует «установить ближе к корню
  диска», что не подходит для случая усечения пути самим
  `GetModuleFileNameW`.
- Повреждённый кеш скачанного архива Python не проходит проверку суммы и
  остаётся на месте, поэтому повторный запуск сборки падает так же, пока файл
  не удалить вручную.

## Пробелы в тестах

- `test_deduplicates_by_path` сравнивает пути в одинаковом регистре, поэтому не
  проверяет правило приведения регистра, которое реализовано.
- Ветка `discover_file_editors` с версионными подкаталогами не покрыта, хотя
  срабатывает именно она на реальной установке 1С.
- Тест успешной проверки атрибутов подменяет только `GIT_CONFIG_GLOBAL`, но не
  `GIT_CONFIG_SYSTEM` и не `HOME`.
- Порядок «сначала реестр, потом удаление каталога» проверяется по результату, а
  не напрямую; именно обратный порядок был причиной серьёзной ошибки, поэтому
  явный тест на порядок был бы уместен.

## Прочее

- `mxl.ico` — временная монограмма, сгенерированная скриптом. При желании
  заменить на настоящую иконку.
- Контрольная сумма `tcltk.msi` зафиксирована после скачивания по TLS: для
  покомпонентных MSI python.org не публикует дайджестов, в отличие от основного
  архива. Provenance слабее, в комментарии к константе это отмечено.
