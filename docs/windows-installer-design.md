# Установка MXL Merge Tool без Python и без командной строки

Дата: 2026-08-04, реализовано и проверено на Windows 2026-08-09
Статус: реализовано. Документ описывает принятые решения и их причины;
открытые вопросы — в `windows-installer-open-items.md`

## Задача

Сегодня установка требует от пользователя установленного Python, скачивания
исходников и запуска `python mxl_tool.py install` с путями к 1С в аргументах.
Для 1С-разработчика это три незнакомых шага подряд, каждый из которых может
провалиться молча.

Цель: пользователь скачивает один архив, распаковывает, делает двойной клик и
получает настроенные diff- и merge-драйверы во всех своих репозиториях. Python
на машине не нужен. Командная строка не нужна.

## Границы

Целевая платформа — только Windows x64. Сборки для macOS и Linux не делаем: там
инструмент запускают из исходников, как сейчас.

Права администратора не требуются ни на одном шаге. Всё пишется в
`HKEY_CURRENT_USER` и `%LOCALAPPDATA%`.

Вне задачи: подпись кода (сертификат недоступен), публикация в winget и
Chocolatey, автообновление, устранение мигающей консоли у `textconv` и
merge-драйвера в Git Extensions.

## Ключевое ограничение: антивирус

Подписи у нас нет и не будет. Неподписанный бинарник, собранный PyInstaller в
режиме `--onefile`, распаковывает себя в `%TEMP%` при каждом запуске — ровно то
поведение, на которое реагируют эвристики антивирусов. В корпоративной среде это
блокер, а не мелкое неудобство.

Поэтому в дистрибутиве нет ни одного упакованного или скомпилированного из
Python бинарника. Интерпретатор — официальный embeddable-пакет Python для
Windows, подписанный Python Software Foundation. Наш код — обычные `.py` файлы.
Единственный собранный нами исполняемый файл — крошечный лаунчер на C, который
не упаковывает и не распаковывает ничего.

## Состав дистрибутива

```
mxl-merge-tool-0.3.0-win64.zip          (~14 МБ)
└─ mxl-merge-tool\
   ├─ MXL merge tool.exe                лаунчер, ~40 КБ
   ├─ runtime\                          python-3.12.x-embed-amd64
   │  ├─ python.exe pythonw.exe python312.dll
   │  ├─ python312.zip
   │  ├─ python312._pth                 + строки ..\app и Lib
   │  ├─ _tkinter.pyd                   из tcltk.msi (python.org)
   │  ├─ tcl86t.dll tk86t.dll zlib1.dll из tcltk.msi, рядом с python.exe
   │  ├─ Lib\tkinter\                   пакет tkinter из tcltk.msi
   │  └─ tcl\tcl8.6 tcl\tk8.6 tcl\tcl8  скрипт-библиотеки Tcl/Tk из tcltk.msi
   ├─ app\
   │  ├─ mxl_tool.py mxl_ui.py mxl_onec.py mxl_preview.py mxl_html.py
   │  │  mxl_subprocess.py mxl_setup.py mxl_setup_ui.py mxl_setup_gui.py
   │  ├─ ui.html mxl.ico
   │  └─ onec\MxlToHtml.epf MxlRendererTemplate.dt
   └─ README.txt
```

`tkinter` не входит в embeddable-сборку Python. Его извлекает
`tools/build_windows.py` из отдельного MSI `tcltk.msi`, который python.org
публикует рядом с обычным инсталлятором. В отличие от `PYTHON_SHA256`, сумма
для этого MSI не публикуется на странице релиза, поэтому она лишь зафиксирована
после первого скачивания по TLS, а не сверена с опубликованным значением —
provenance слабее. Из MSI берётся только `_tkinter.pyd`, три DLL, пакет
`tkinter` и скрипт-библиотеки `tcl8.6`/`tk8.6`/`tcl8` — без IDLE, turtledemo,
import-библиотек и Tix (это ещё 4.2 МБ, инструменту не нужных).

`README.txt` содержит запасную строку запуска через `runtime\python.exe` — на
случай, если политики домена заблокируют исполняемый файл.

## Лаунчер

Один файл на C, около пятидесяти строк. `GetModuleFileNameW` даёт собственный
путь, `CreateProcessW` запускает `runtime\pythonw.exe app\mxl_tool.py` с
аргументами командной строки, переданными как есть. Без аргументов подставляется
`setup-gui`. Тот же исполняемый файл обслуживает пункты контекстного меню.

Три обязательных свойства сборки:

- Подсистема `/SUBSYSTEM:WINDOWS`, не console. Консольное окно не появляется
  вообще — этого вариант с `.cmd` дать не мог.
- Ресурсы VERSIONINFO и иконка. Исполняемый файл без сведений о версии выглядит
  подозрительно и для пользователя, и для эвристик антивируса.
- Имя файла не содержит слов `setup`, `install`, `update`, `patch` и их русских
  аналогов. Windows определяет установщики по имени файла и автоматически
  требует для них повышения прав. Манифест задаёт `asInvoker`, повышение прав не
  запрашивается.

Статическая линковка, внешних зависимостей нет.

## Первый запуск

1. Лаунчер запускает `mxl_tool.py setup-gui`.
2. Команда копирует `runtime\`, `app\` и сам лаунчер в
   `%LOCALAPPDATA%\mxl-merge-tool\0.3.0\`, после чего перезапускает себя уже из
   этого каталога и завершает исходный процесс. Всё дальнейшее выполняется
   оттуда, поэтому распакованный архив можно удалить сразу. Запуск лаунчера,
   который уже находится в целевом каталоге, копирование пропускает.
3. Открывается нативное окно на tkinter. Первая редакция показывала страницу в
   браузере через loopback-сервер с токеном сессии; от этого отказались после
   того, как пользователь попросил нативный интерфейс.
4. Окно показывает результат автопоиска: `git.exe`, тонкий клиент 1С,
   «1С:Предприятие — Работа с файлами». Каждое поле можно изменить: выбрать
   другую версию из выпадающего списка или указать путь вручную.
5. Кнопка «Установить» вызывает существующий путь `install --global`, передавая
   найденные пути как `--onec-client` и `--onec-file-editor`. Затем
   регистрируются контекстное меню, ярлыки настройки и удаления в меню «Пуск»
   и запись для удаления.
6. Экран «Готово» перечисляет настроенное и предлагает кнопку «Проверить»,
   которая прогоняет `git check-attr diff merge` на временном файле и
   показывает результат.

Отсутствие 1С не блокирует установку: diff и слияние работают без платформы,
недоступным остаётся только точный HTML-предпросмотр.

## Автопоиск

Тонкий клиент 1С ищется в следующем порядке:

1. Ключ реестра `HKLM\SOFTWARE\1C\1Cv8` и его аналог в `HKCU`.
2. Каталоги `%PROGRAMFILES%\1cv8\<версия>\bin\1cv8c.exe` и
   `%PROGRAMFILES(X86)%\1cv8\<версия>\bin\1cv8c.exe`.

«Работа с файлами» ищется как `1cv8fv.exe` в `%PROGRAMFILES(X86)%\1cv8fv\bin` и
`%PROGRAMFILES%\1cv8fv\bin`.

Версии сортируются как кортежи чисел, по умолчанию предлагается старшая.
Найденные варианты передаются в интерфейс списком, выбор пользователя
приоритетнее автоматического.

Для тонкого клиента дополнительно проверяется наличие `1cv8.exe` рядом с
`1cv8c.exe` — без него пакетный рендер не заработает. Если файла нет, интерфейс
предупреждает, но установку не блокирует.

## Контекстное меню

Регистрация в `HKCU\Software\Classes`, два ключа:

- `Directory\shell\MxlMergeTool` — правый клик по папке репозитория.
- `Directory\Background\shell\MxlMergeTool` — правый клик по пустому месту
  внутри открытой папки.

Обе команды запускают
`"%LOCALAPPDATA%\mxl-merge-tool\<версия>\MXL merge tool.exe" setup-repo "%V"`,
подпись пункта — «MXL merge: настроить этот репозиторий», иконка берётся из
`mxl.ico`.

Реестр не умеет показывать пункт условно, поэтому проверку выполняет сама
команда. Если каталог не является рабочим деревом Git, открывается та же
страница с понятным сообщением. Отдельных диалогов об ошибках не заводим:
интерфейс во всех случаях один и тот же.

Пункт нужен нечасто, поскольку глобальная настройка уже покрывает все
репозитории. Его назначение — дописать `.gitattributes` в конкретный проект и
служить точкой диагностики.

## Обновление и удаление

Обновление: распаковать новый архив и запустить лаунчер. Файлы кладутся в
каталог своей версии, конфигурация Git перезаписывается. Этот шаг обязателен при
каждом обновлении — `TEXTCONV_FORMAT_VERSION` (сейчас `"2"`) входит в ключ кеша
textconv, и без переустановки Git вернёт устаревший результат diff.

В `%APPDATA%\Microsoft\Windows\Start Menu\Programs\MXL Merge Tool` создаются
два ярлыка: настройка запускает установленный лаунчер с аргументами
`setup-gui --installed`, удаление — с аргументом `uninstall`. При обновлении
ярлыки перезаписываются и поэтому всегда ведут на каталог текущей версии.
Чтобы Windows 11 не схлопывала два ярлыка с разными аргументами в одну запись,
при копировании дистрибутива создаются два идентичных launcher-alias:
`MXL Merge Tool Settings.exe` и `MXL Merge Tool Maintenance.exe`. Ярлыки ведут
на разные пути, но оба лаунчера исполняют тот же код. Дополнительно через
`IPropertyStore` им записываются разные явные `System.AppUserModel.ID`:
`MxlMergeTool.Desktop.Settings` и `MxlMergeTool.Desktop.Maintenance`. Поэтому
Shell не зависит от эвристик по одинаковым PE-метаданным двух лаунчеров.
После атомарного переименования ярлыка установщик вызывает `SHChangeNotify` с
`SHCNE_RENAMEITEM` и `SHCNE_UPDATEDIR`, чтобы кеш меню «Пуск» сразу увидел
финальное Unicode-имя. При удалении папки ярлыков отправляются `SHCNE_RMDIR` и
обновление родительского каталога.

Удаление запускается ярлыком в меню «Пуск», а запись в
`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\MxlMergeTool` даёт
пункт в «Программах и компонентах». Команда `MXL merge tool.exe uninstall`
сначала показывает системный диалог подтверждения с безопасным ответом «Нет»
по умолчанию. После подтверждения команда
снимает ключи `diff.mxl.*`, `merge.mxl.*`, `mergetool.mxl.*` и `mxl.*` из
глобальной конфигурации Git, удаляет ключи контекстного меню и запись об
удалении, папку ярлыков, затем чистит `%LOCALAPPDATA%\mxl-merge-tool`. Файл
`.gitattributes` в репозиториях пользователя не трогается — он под контролем
версий и принадлежит проекту, а не инструменту.

## Сборка

Сборка локальная, на машине разработчика под macOS. Готового CI в репозитории
нет, и эта задача его не заводит.

`tools/build_windows.py` выполняет:

1. Скачивает embeddable-архив Python по зафиксированным версии и контрольной
   сумме SHA-256. Несовпадение суммы прерывает сборку.
2. Дописывает `..\app` в `python312._pth`, чтобы модули приложения попадали в
   `sys.path`.
3. Компилирует лаунчер: `x86_64-w64-mingw32-gcc -static`, ресурсы через
   `x86_64-w64-mingw32-windres`. Пакет ставится командой
   `brew install mingw-w64`.
4. Собирает дерево каталогов и упаковывает в ZIP, рядом кладёт файл с SHA-256.

Если компилятор в системе не найден, скрипт собирает архив с `Настроить.cmd`
вместо лаунчера и помечает его как dev-сборку. Это позволяет получить рабочий
пакет без mingw, но такой архив не публикуется.

Публикация релиза — вручную через веб-интерфейс GitHub: ZIP и файл с контрольной
суммой прикрепляются к тегу.

Собранный mingw бинарник теоретически привлекает внимание эвристик чуть больше,
чем собранный MSVC. Поскольку CI с MSVC у нас нет, эту проверку заменяет
обязательный прогон готового архива на Windows-стенде с тем антивирусом, который
стоит у пользователей, до публикации.

## Изменения в коде

Логика установки разделена на два модуля с разными ответственностями и
разными способами проверки:

- `mxl_setup.py` — автопоиск 1С и Git, копирование в `%LOCALAPPDATA%`, работа с
  реестром, удаление. Доступ к реестру и файловой системе изолируется за узким
  интерфейсом, поэтому эту логику можно проверять подменой на любой платформе,
  без реального Windows-окружения.
- `mxl_setup_ui.py` — точки входа `run_setup` и `run_repo_setup`, проверка
  установки и сборка данных для интерфейса.
- `mxl_setup_gui.py` — само окно на tkinter. Виджеты держатся тонким слоем над
  чистыми функциями, которые из `Discovery` собирают подписи списков и текст
  предупреждений, — именно они и покрыты тестами, поскольку кликать по окну в
  наборе тестов нельзя.

Новые подкоманды в `mxl_tool.py`: `setup-gui`, `setup-repo`, `uninstall`. Все
три — тонкие обёртки над `mxl_setup.py`. Существующий `install` не меняется: он
уже поддерживает `--global` и учитывает `sys.frozen`.

Интерфейс установки отделён от интерфейса разрешения конфликтов: `ui.html`
остаётся браузерным и своего механизма не меняет, окно установки — нативное.
Смешивать их не нужно, а `ui.html` уже занимает 159 КБ.

tkinter не входит в embeddable-пакет Python, поэтому окно установки повлекло за
собой упаковку `_tkinter.pyd`, DLL Tcl/Tk и скрипт-библиотек из `tcltk.msi`.
Это цена нативности: архив вырос примерно с 12 до 14 МБ, а к сборочным
зависимостям добавился `msitools`.

`mxl_tool.py` разросся до 3572 строк, поэтому новая логика в него не
добавляется.

Новый скрипт `tools/build_windows.py` и исходник лаунчера в `tools/launcher/`.

## Проверка

Автоматически, на любой платформе:

- Разбор версий 1С и выбор старшей.
- Формирование команд контекстного меню и путей.
- Полный цикл установки и удаления на подменённых реестре и файловой системе.

Вручную, на Windows-стенде — обязательный чек-лист перед публикацией:

1. Распаковать архив в «Загрузки», запустить лаунчер двойным кликом.
2. Убедиться, что консольное окно не появляется и запрос UAC не возникает.
3. Проверить, что 1С найдена автоматически и обе версии подставлены верно.
4. Нажать «Установить», дождаться экрана «Готово», нажать «Проверить».
5. Удалить распакованный каталог, открыть репозиторий с конфликтным `.mxl`,
   выполнить слияние и убедиться, что интерфейс открывается.
6. Проверить оба пункта контекстного меню — на папке и на её фоне.
7. Проверить пункт в «Программах и компонентах»: удалить, убедиться, что ключи
   Git и реестра сняты, каталог удалён, `.gitattributes` не тронут.
8. Проверить реакцию антивируса на распакованный архив и на лаунчер.
